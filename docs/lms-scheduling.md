# Step 7C: schedules, lessons and timetable

## Inspection and implementation plan

Baseline `1ee517c` is clean; strict TypeScript and all 194 portable tests pass. Local app port 3000 and Supabase Auth port 54321 respond. Installed Next.js Server Actions/data-security guides, the group/teacher/enrollment schema, composite identity keys, role helpers, versioned commands and UI patterns were inspected before coding. Existing local services/data are reused. No dependency, hosted service, database reset or separate student/teacher identity is needed.

Only 7C is authorized: weekly group schedules, lesson generation/individual records/lifecycle, substitutions, expected rosters, timetable and conflict protection. Full Student Profile timetable/dashboard/invoice integration remains 7D; attendance marking, payroll, billing and drag-and-drop remain outside this increment.

Weekly schedules use explicit local weekday/time, IANA timezone and a bounded effective period of at most one year. Multiple weekly series can belong to a group. Editing creates a new effective revision and closes the old period; generated lessons remain unchanged and keep source revision/date references. Generation is bounded and atomic, with one root lesson per schedule series/local occurrence date. Cancelled/rescheduled roots remain receipts, so regenerating cannot resurrect them. Unmaterialized weekly occurrences reserve resources; materialized occurrences use their concrete lesson resources instead.

Lesson timestamps are timezone-aware UTC instants, with the intended timezone retained. Local times are validated in PostgreSQL; nonexistent or ambiguous daylight-saving times are rejected, never silently shifted or assigned an arbitrary offset. Recurring slots stay within one local day; individual lessons can cross midnight with a maximum 24-hour duration. Scheduled, in-progress and completed lessons block overlaps; cancelled/rescheduled records release their occupied time. Adjacent end/start times are allowed. Effective substitute teachers replace the original teacher's occupied time. Conflict checks cover teacher across business branches, group and classroom, including unmaterialized schedules, under the existing tenant transaction lock and database triggers.

Groups/branches/courses/classrooms/employees/student identities are reused. Primary lesson teachers require current eligible group assignments; substitutes need eligible branch teaching authorization but do not require permanent group assignment. Ordinary managers operate in actual authorized branches; teachers see authorized group lessons or their explicit lesson assignment. Completion is separate from lesson management and limited to the actual teaching employee unless the user has management permission. No academic grant exposes financial information.

Lifecycle and roster rules will be documented and tested explicitly. Upcoming lesson metadata can be edited; moving time creates a linked replacement and marks the source rescheduled. Completed/cancelled/rescheduled records are retained and immutable. Expected rosters use existing enrollment IDs and effective periods and freeze on start/completion; they never mark actual attendance. Schedule/history receipts are private and all changes have actor/reason/before/after records. Resource deactivation/reassignment does not silently rewrite historical lessons; future generation revalidates eligibility.

Validation plan: real portable/native/live tests for recurrence retries and rollback, future revisions, UTC/DST conversion, overlap/adjacency across branches, substitutes/online groups, completed immutability, expected roster identity, role/tenant/branch isolation, concurrent bookings, unchanged financial sources, and full regression/build/types/format checks. UI reuses existing forms, pagination, responsive components and protected navigation. No deployment or remote push is part of this increment.

## Weekly periods and generation

A weekly series represents one weekday/time pattern. Add separate slots for Monday/Wednesday/Friday, additional same-day sessions or different times. Each enabled revision has a concrete end date no more than 365 days after its start, and must fit the group's dates. Recurring start/end are on the same local day. New periods start today or later in their own timezone. Teachers need current eligible group assignments; optional rooms must be active, in the group branch and cover maximum group capacity. Online teaching uses a null room.

Revision closes the previous period before the new effective start, or disables a not-yet-started old period, then creates a new row in the same series. The old row/definition/history remains. Only the latest current/future revision is editable. Ending a weekly period stops unmaterialized occurrences from a chosen date; it does **not** cancel or edit already-generated lessons. The UI shows the number of future scheduled lessons in the series and links to review them individually.

Generation accepts at most 31 local dates per request. Each slot interprets those dates in its own retained timezone; the lower range cannot precede business-local today. Already-past start instants are counted and skipped. A unique root key `(tenant, series, local occurrence date)` prevents duplicates across concurrent requests, revisions and retries. Cancelled/rescheduled roots still occupy that identity, so generation never resurrects them. Rescheduled replacements retain their source slot/date/revision lineage. A matching request ID/actor/payload returns the original batch receipt; different payload reuse is rejected. Fresh generation requests count existing occurrences without duplicating them. An invalid resource/conflict in any occurrence rolls back the entire batch, including earlier lesson/event inserts and the request receipt.

## Timezones, conflicts and resource changes

Weekly clocks retain an IANA timezone (defaulting to the business timezone, initially Asia/Tashkent). Concrete lessons use PostgreSQL `timestamptz` instants, with their intended timezone alongside them. Individual date/time inputs are interpreted in that explicit timezone in PostgreSQL; browser/device timezone is not authority. Lesson details display their retained timezone. The timetable displays all authorized events in the **business timezone**, making cross-zone comparisons consistent.

The converter checks the wall-clock round trip and candidate offsets around transitions. Nonexistent and ambiguous times are rejected, including one-hour and half-hour daylight-saving changes. No arbitrary duplicate-hour offset is silently chosen. Choose an unambiguous time or split the effective weekly period around a transition. Valid local clocks retain their intended local hour when the UTC offset changes. Individual lessons may cross midnight up to 24 elapsed hours; recurring slots stay within one local day. Calendar date arithmetic uses UTC date-only values to avoid browser DST drift; the query uses actual business-local day boundaries.

Intervals are half-open: one lesson can end exactly when another starts. Scheduled, in-progress and completed lessons block resource overlap; cancelled and rescheduled sources release their old occupied time. Checks cover the group, **effective** teaching employee and physical room across the whole business, including different branches. The substitute occupies the time instead of the original teacher. A teacher account in another tenant is an independent employee/resource; no cross-tenant scheduling information is exposed.

Unmaterialized weekly occurrences also reserve those resources over their complete bounded period. Once an occurrence is generated, its concrete lesson becomes the booking authority. This allows an authorized one-off teacher/room change to release the original resource without rewriting the weekly pattern. A replacement moved onto another ungenerated occurrence is still checked against that occurrence; a cancelled root does not leave a phantom reservation. Weekly-definition, individual-booking and concurrent-generation tests exercise these rules.

No arbitrary double-booking/capacity bypass exists. Supported authorized exceptions are an eligible substitute, online instruction without a physical room, or reasoned cancellation/rescheduling. Future generation revalidates current teacher/branch/room eligibility. HR/role deactivation preserves historical references while revoking account access; it does not silently reassign lessons. Room/group capacity changes cannot invalidate scheduled alternative rooms or current weekly teaching plans. Group date changes must retain existing lesson and enabled schedule periods. Before completing/cancelling/archiving a group, end its current/future weekly periods and finish/cancel outstanding lessons, as well as closing reserved enrollments under 7B.

## Lifecycle, rosters and permissions

New lessons start scheduled. Only upcoming scheduled metadata (topic/notes/teacher/substitute/room) can be edited. Moving time or changing its timezone context uses **Reschedule lesson**, which atomically marks the original rescheduled and creates a linked scheduled replacement. A failed move leaves the original/history unchanged. Cancelled, rescheduled and completed records cannot be overwritten or deleted. Rescheduling requires an upcoming source and future target. Authorized managers can record past scheduled entries with a reason and complete them separately; generation does not manufacture past sessions.

Starting requires scheduled time to have arrived and an active group/branch. Completion requires scheduled end to have passed. Starting/completing freezes the expected enrollment IDs once; completion without an intermediate start also captures the list. No presence, absence, attendance score, invoice or salary calculation is recorded. Expected lists compare enrollment dates with the lesson's retained local date, use existing status (active/completed/withdrawn periods), select one relevant enrollment per student and exclude currently pending/paused/cancelled agreements. A captured list preserves those identities through later pauses/transfers/withdrawal. The calendar's business timezone is a display/query preference, not a rewrite of the lesson's local academic date. Backfilled entries use the enrollment facts available when captured; this is not historical attendance reconstruction. Date-level transfer periods are inclusive, so both old/new groups may expect a student on a transfer day. Future attendance can record what actually happened.

Owner/Admin manage own-business schedules and lessons; Branch Managers manage actual assigned branches. The equivalent existing `lessons.view`/`lessons.manage` permissions are reused, with `schedules.view/manage` and `lessons.complete` added. Teachers have schedule/lesson reads within assigned group scope and their own explicit lesson assignment, including one-off substitutes without permanent group assignment. Personal timetable defaults to **My teaching**; choosing all authorized teachers preserves that choice across pages/period navigation. A substitute can read their lesson and minimal expected roster without gaining whole-group/CRM access.

Without lesson management permission, starting/completing additionally requires the logged-in employee to be the **actual** teaching employee. Another assigned group teacher cannot complete their colleague's lesson merely because they can view it. Teachers cannot manage weekly plans, create/edit/cancel/reschedule lessons, assign substitutes or read finance/salary via these APIs. Expected roster reads also require enrollment-view permission and expose name/identifier/academic references only; canonical Student Profile links still use existing whole-contact CRM checks. No agreed tuition, private enrollment notes, guardian/contact detail, debt, payment or salary is joined into scheduling DTOs.

## Manual walkthrough

No new dependency, credential or environment variable is required on this configured machine. Open <http://127.0.0.1:3000>. If restarting later, start Docker Desktop and run `npm run db:start`, `npm run db:migrate`, `npm run dev`; preserve existing data and never reset to apply these migrations.

1. As Owner/Manager, open an existing group. Ensure its branch is active and it has eligible linked employee teachers from 7B. Choose **Weekly schedules → Add weekly slot**. Pick weekday, local time, timezone, teacher, optional classroom and effective start/end. Add another slot for each other teaching weekday.
2. Choose **Generate lessons**, initially for the next seven days. Check the actual created/existing/past-skipped receipt. Repeat the same range: existing occurrences must remain, with no duplicate lessons. Open group lessons or the timetable.
3. On **Timetable**, try Daily/Weekly/Monthly and branch/course/group/teaching-employee/room/status filters. Use previous/next period and click a lesson. Dates use the business timezone. Weekly plans need generation to appear as concrete calendar events; their unmaterialized reservations still protect booking operations. Narrow filters or page through events when the calendar exceeds 200 lessons.
4. Choose **Add lesson** for an authorized group. Confirm explicit local times/timezone and assigned teacher, optional substitute/room, title and reason. Try an overlapping room, teacher across branches or group: the save must fail without partial data. Adjacent periods should succeed; online lessons can leave the room empty.
5. Edit an upcoming lesson's topic/room/substitute. Use **Reschedule lesson** to move time. Verify the original rescheduled record and replacement link. Cancel an occurrence with a reason, then regenerate its original weekly range: it must remain cancelled/rescheduled. If a move conflicts, the source remains unchanged.
6. Revise a weekly period from a future date. Check old/new effective history and verify previously generated future lessons keep their original times. Review and reschedule/cancel those lessons individually when necessary. End a period and confirm existing lessons remain.
7. When a lesson has started, start it; after its end, mark it completed. For convenient local testing, an authorized manager can create a past lesson within the group's date range, with a reason, and complete it. Confirm expected enrollment/Student Profile links are captured and later enrollment changes do not replace those identities. Completed lessons must reject edits/cancellation. This does not mark attendance.
8. Use separate browser profiles for Teacher, a one-off Substitute, branch-limited Manager, ordinary Employee and another business. Teacher sees permitted teaching records and cannot finish a colleague's lesson. Substitute sees only authorized lessons/expected names without whole-group or tuition/finance access. IDs/cookies cannot authorize other branches/businesses. Archive a linked employee and verify access is revoked while Owner history remains.
9. Open an original Student Profile with guardians/invoice/payment history. Verify original IDs, debt/credit and invoice links remain unchanged after scheduling. No charges or payroll should appear. For daylight-saving QA, use an appropriate group period and America/New_York; a missing/duplicate local hour must reject, while an unambiguous hour displays its intended local time.

Automated commands: `npm run check`, `npm run db:test`, `npm run db:lint`; with the server running, `npm run test:integration` and `npm run test:smoke`. Portable tests execute actual migration SQL in isolated embedded PostgreSQL. Native fixtures roll back; live test accounts/business records are real isolated local fixtures retained for inspection. Remaining manual QA includes visual/mobile/keyboard/focus, browser-native confirmations, earlier password-recovery link redemption/sales dragging/print layout and production-size load.
