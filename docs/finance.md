# Financial foundation — Step 6A

This increment implements cashboxes and the operational cash ledger only. Invoices/receivables (6B), payments/allocations/credit (6C), expenses/transfers/refunds/reversals (6D), and financial dashboards/reports/exports (6E) are deliberately deferred. Opening balances and reasoned adjustments are the only posting workflows currently exposed. Adjustments are not payment, expense or refund records.

## Data and exact money

| Table                      | Responsibility                                                                                                                                                                                    |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `finance_currencies`       | Reviewed currency catalog; only UZS with two fractional digits enabled                                                                                                                            |
| `cashboxes`                | Tenant, optional branch, name/type/currency/status, creator, timestamps and optimistic version; no balance column                                                                                 |
| `financial_transactions`   | Immutable posting envelope, tenant-wide unique request key, canonical request payload, kind/currency/reason, authenticated actor/name snapshot, optional linked HR employee and posting timestamp |
| `financial_ledger_entries` | Signed exact cash movements referencing an envelope and a same-tenant, same-currency cashbox                                                                                                      |
| `financial_audit_events`   | Append-only cashbox creation/configuration before/after details and each committed posting's actor, reason, exact amount and timestamp                                                            |

Migration `20261023000900_financial_foundation.sql` adds this schema, RLS, grants, triggers and permission backfill. `20261023001000_financial_cashbox_rpcs.sql` adds checked command/query RPCs. `20261023001100_financial_posting_integrity.sql` prevents appending extra movements to existing posted envelopes. All preserve previous records. Existing `private.has_permission` remains the single authorization engine. No financial sample records are seeded.

Individual ledger movements use PostgreSQL **NUMERIC without a typmod**, with explicit nonzero, two-place exactness and magnitude checks equivalent to `NUMERIC(18,2)` (maximum absolute movement `9999999999999999.99`). An unconstrained numeric plus a precision CHECK is intentional: a `NUMERIC(18,2)` column would round an invalid third fractional digit before its CHECK ran. Inputs accept ordinary decimal strings with at most 16 integer and two fractional digits; exponent notation, separators, nonfinite values and excess precision are rejected. Valid inputs are normalized to two places. PostgreSQL performs every sum and comparison using exact NUMERIC. Aggregate balances can exceed an individual movement's maximum.

Monetary tables have no direct client SELECT grants. Checked query RPCs explicitly cast each amount and balance to **text** before JSON leaves PostgreSQL. The TypeScript ledger/directory DTOs use strings. Input validation and formatting split/group strings without `Number`, `parseFloat`, float arithmetic or numeric JSON transport. Only record counts and page numbers use JavaScript numbers. Large-value tests cover values above JavaScript's safe integer boundary through SQL, actual PostgREST and rendered pages.

Cashbox currency and branch are immutable. The currency catalog, composite currency foreign keys, envelope currency and per-currency values allow future currencies without combining unlike money. Another currency/precision must be enabled by a reviewed migration; no exchange, cross-currency posting or currency switching exists. UZS uses two fractional places consistently. This is operational money tracking, not a statutory accounting, tax or full double-entry general-ledger system.

## Posting and concurrency contract

`save_cashbox` requires view+manage in the actual branch, or both business-wide for an unscoped cashbox. Create uses a stable UUID request key with canonical original details and creator identity. Exact retries return the existing ID, even if the cashbox was subsequently renamed. Reuse for different details fails. Edits lock the cashbox and compare the submitted version, retain scope/currency, and append before/after audit data. No client delete workflow exists, including for unused boxes.

`post_cashbox_entry` requires view+adjust in the cashbox's actual scope. It takes decimal text, an explicit reason and request key. Actor, optional employee, currency and posting time come from authenticated/database records, never frontend assertions. A transaction acquires a request-key advisory lock and then a row lock on the cashbox. Exact committed retries return the original transaction ID; changing cashbox, amount, kind, actor or reason under that key fails. Unique constraints remain the final idempotency defense. Authorization is still checked for a retry, including employee/membership status.

An opening balance must be positive and the first movement; an empty box already has a zero calculated balance. The first movement may instead be an adjustment, which closes the opening-balance opportunity. An adjustment is a signed delta, never an editable target balance. Negative resulting balances are blocked for every 6A operation. Configuration edits/deactivation use the same cashbox row lock, so postings and status changes serialize. The default insufficient-balance rule and currency constraint will also apply when later outflow/transfer workflows are introduced; configurable exceptions are not implemented in 6A.

The envelope, ledger movement and audit event commit together. A deferred constraint trigger requires exactly one ledger leg and its matching cashbox/kind audit event for each current posting. First-opening uniqueness, branch/currency references and amount checks also exist independently of the UI. All envelopes, movements and audit events reject UPDATE/DELETE through database triggers, including accidental ordinary privileged DML. Cashboxes reject deletion or changes to creation identity/scope/currency. As with the rest of PostgreSQL, a trusted database administrator who deliberately disables safeguards is outside the tenant-user threat boundary.

Future payment/expense/refund records should reference their unique posting envelope. Payment allocations will affect receivables/credit, not cashbox movement; unallocated credit will be derived from net payment/allocation/refund records. Each invoice owns one branch even when its customer spans branches. Transfers will add one locked, atomic envelope with opposite signed same-currency legs and explicit source/destination authorization, and extend the deferred kind-specific invariant. Reversals will link a new correction to its original envelope; they must never rewrite it. These workflows require their own constraints and tests in their scheduled increments, rather than relaxing the current one-leg invariant prematurely.

## Access rules

| Default role                       | Current finance access                                                                                                     |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Owner / Admin                      | View/manage/adjust/audit throughout their own business                                                                     |
| Branch Manager                     | View/manage assigned-branch cashboxes; cannot post adjustments or read separate audit detail by default                    |
| Cashier                            | Read cashboxes and posted history in assigned branches; existing future payment grants do not enable payment workflows yet |
| Teacher / Employee / Sales Manager | No finance access by default                                                                                               |
| Custom role                        | Explicit existing-engine grants, checked independently in each actual scope                                                |

Reused: `cashboxes.view`, `cashboxes.manage`. Added: `cashboxes.adjust`, `finance.audit.view`. Existing payment permissions are unchanged. Later increments will add their specific remaining permissions. New-tenant setup and existing system-role backfill receive the same defaults. Custom grants are preserved. Business-wide cashboxes require business-wide view/operation permission; branch grants cannot authorize them. Branch permissions are never unioned to authorize another branch. Deactivated/archived linked HR employees and suspended memberships lose access immediately. Record actor snapshots remain for historical attribution.

All tenant finance tables have RLS, tenant-scoped composite foreign keys and no direct client mutation grants. Only cashbox metadata columns and the currency catalog have client SELECT grants. Ledger/audit query RPCs perform explicit current-subject checks. Financial transaction RLS requires access to **every** associated cashbox, so future multi-leg envelopes cannot expose a hidden counterpart. Audit visibility additionally requires `finance.audit.view`; ordinary ledger history is available with cashbox view. Server actions independently validate the current workspace and operation scope before calling the RPC. IDs and cookies are preferences/input, never authority. No service-role credentials or platform-admin features are used.

## Pages and date semantics

`/finance` explains the currently available foundation. `/finance/cashboxes` supports literal name search, authorized branch/business scope, type, status, exact-balance/name/newest sorting, and 20-record pages. The selected branch is the default when permitted; selecting “All permitted cashboxes” includes every visible branch and authorized business-wide boxes. Creation is at `/finance/cashboxes/new`; each detail page has an `/edit` page.

Details show the all-time calculated balance and paginated immutable ledger. Inclusive date, posting type and recorder filters apply only to history, never to the current balance. Dates use the business IANA timezone and half-open UTC timestamp bounds. Step 6A entries use database posting time; user backdating/future effective dates are not supported. Recorder choices show up to 200 historical actors for that cashbox, including people who later leave. Separate audit history paginates 20 and checks its own permission. No global report/export or financial dashboard totals are implied.

Posting forms require an explicit acknowledgement plus browser confirmation, disable pending submits, and redirect after successful posting. A retained request key protects resubmission of the same request. Refreshing a form starts a new request; idempotency does not infer whether two separately entered legitimate corrections describe the same real-world event. Check history after an uncertain outcome. Validation failures leave clear feedback. Loading/error states and horizontal table scrolling reuse existing patterns. Next may return HTTP 200 for an already-streamed `notFound()` response; denial UI/noindex and absence of protected records are tested along with database denial.

## Local verification walkthrough

1. Start Docker Desktop. In the project, run `npm run db:start`, `npm run db:migrate`, then `npm run dev` if port 3000 is not already serving the app. Keep using the existing loopback `.env.local`; no hosted configuration is needed.
2. Open **http://127.0.0.1:3000**, sign in as an Owner, choose a business/branch and open **Finance → Cashboxes**.
3. Create a cashbox named “Front desk”, with an active branch and UZS. Its balance must be **0.00 UZS**. Open it and post an opening balance of **100.10** with a reason and confirmation. Post an adjustment of **-0.10**. Expect **100.00 UZS**, two immutable postings and creation/posting audit records.
4. Try `0`, `0.001` and `-100.01`. Expect validation/rejection and no balance change. A second opening is unavailable and rejected by direct RPC too. Reload/duplicate the same request to check idempotency; deliberately new requests are separate operations.
5. Edit the name/type, deactivate, and inspect history. No posting form should remain, and direct postings must fail. Reactivate and confirm history/balance are retained. An old edit form must fail its version check. Branch/currency cannot be moved.
6. Create a second branch cashbox and a business-wide one. In separate browser profiles, test an assigned Cashier (read-only), a Branch Manager (assigned-branch management only), ordinary Employee/Teacher (no finance), and another business Owner. Paste unauthorized detail/edit URLs and alter IDs in RPC/forms; no protected money or operations should become available. Deactivate a linked employee and verify access is revoked.
7. Check date/type/recorder filters and pagination, including business-local midnight. The current balance must remain all-time. Review layout, mobile scrolling, keyboard focus, checkbox and native confirmation dialogs manually.
