# Expenses, transfers, refunds and corrections (6D)

All operations use local Supabase and actual records. Money remains exact decimal text at the application boundary and PostgreSQL NUMERIC internally. This is an operational cash ledger, not statutory accounting, payroll settlement or tax reporting.

Expenses have an immutable branch, cashbox, category snapshot, vendor, description, effective timestamp and positive amount. Posting creates one negative ledger entry. Owner/Admin can create, rename and deactivate expense categories; configuration changes retain actor/before/after audit. Manager defaults allow expense entry in assigned branches, without business category management. Historical category names remain unchanged.

Transfers require access and `cashboxes.transfer` in both actual cashbox scopes. They require distinct active cashboxes in the same currency and post exactly two opposite entries atomically. A branch grant cannot authorize a business-wide box or a hidden branch. Business totals must exclude transfers from received revenue and expenses. Cashbox balances always derive from every posted ledger entry.

Refunds originate on the original payment page and require `payments.refund`. Total refunds cannot exceed the original payment. They consume available credit first, then release original allocations newest first until sufficient credit exists. Each release requires payment allocation and invoice permissions in that invoice's actual branch, so unauthorized hidden allocations cause the entire command to roll back. Released allocations reopen invoice receivables. Refund cash, releases and audit commit together; insufficient cash rolls everything back. The paying cashbox must match the original payment's branch or be business-wide, with the same currency. Refunds cannot precede the payment's second.

Eligible opening balances, adjustments, expenses and transfers can be corrected from their posting page. A reversal creates exact opposite legs, links its original posting and requires a reason and `finance.reverse` for every original cashbox. Expenses also require expense access. Only one reversal is permitted. Payments use linked refunds; payment/refund/reversal envelopes cannot themselves be reversed. Originals remain immutable and visible. A correction can fail when an active cashbox/branch or sufficient cash is unavailable. Financial date inputs have second precision in the business timezone. Effective and recorded times remain separate; legacy entries retain their original recorded time as effective time.

Cashboxes reject negative balances by default. Only the tenant's actual owner can change `allow_negative`, with a version check, confirmation and reason in the cashbox audit. Admin/Manager cannot enable overdrafts merely by editing cashbox metadata. A negative box must be restored to nonnegative before disabling the policy.

Optional expense receipts live in the private `finance-receipts` Storage bucket (PDF/PNG/JPEG/WebP, at most 5 MiB). Attach after saving the expense; a failed upload does not reverse an already posted expense. The server checks content signatures and current expense-create access. Storage independently checks the authenticated uploader and actual expense scope. Paths contain tenant/expense IDs plus a random filename. No overwrite/delete policy is granted. Downloads require current expense-view access; signed download links expire in 60 seconds. The detail page lists up to 100 receipts per expense. Portable SQL tests omit Supabase-owned Storage; native policy assertions and live Auth/Storage upload/download/isolation tests cover it.

Deferred constraints enforce source/transaction/ledger/audit consistency, exact reversal legs, balanced transfers, refund caps and allocation caps even if a future command is faulty. Posting tables have RLS and no direct browser monetary SELECT/DML grants. Tenant command serialization, cashbox row locks and exact payload idempotency prevent partial or duplicate postings and concurrent overspending. No existing history is rewritten.

Local testing: `node --test tests/financial-operations.test.mjs tests/financial-time.test.mjs`, `npm run db:test`, and `node --env-file=.env.local --test tests/integration/financial-operations.test.mjs`. In the UI, create two branch cashboxes, fund one, post an expense, attach a receipt, transfer between the boxes, reverse the expense, then receive an allocated payment and refund it in two parts. Verify both cashbox histories, reopened invoice debt, refund limits and another tenant's denial. Browser visual/mobile/native-confirmation review remains a separate manual check.
