# Step 8A — Core student attendance

This increment adds core attendance only. Advanced scheduling/holidays (8B), make-ups and delivery extensions (8C), and attendance analytics/exports/full Student Profile summaries (8D) remain separate increments. Existing Step 7 schedules, generation, rescheduling, cancellations, substitutes, timetable, enrollments and finance remain in place.

Inspection started from clean commit `855556c`. Local Auth and Next.js responded on ports 54321/3000; all 225 baseline portable tests passed. Installed Next.js Server Actions and data-security documentation was read before coding. Inspection confirmed that `student_profiles(tenant_id, customer_id)` is the shared Student Profile identity, teachers are existing linked employees, and lessons reference groups/branches with retained enrollment and rescheduling history. Step 7's expected list was not a historical attendance register: it used current enrollment status and saved expectations at lesson start/completion. Attendance therefore uses the existing immutable enrollment audit to review historical eligibility without rewriting the earlier expected-list snapshots.

## Data model and migrations

- `20261026000400_attendance_schema.sql`: `lesson_attendance_sheets`, `lesson_attendance_records`, `attendance_events`, constraints/indexes, RLS, permissions, historical eligibility and integrity helpers.
- `20261026000500_attendance_commands.sql`: checked prepare, draft save, roster review, finalize and finalized-correction commands; exact actor/payload-bound receipts reuse the existing academic command mechanism.
- `20261026000600_attendance_queries.sql`: minimal sheet/roster/history DTOs, teacher workspace, filtered saved attendance history and authorized options.
- `20261026000700_attendance_access_contract.sql`: checked lesson-navigation access query and a lint-only cleanup of the existing attendance command contract. No existing records are rewritten.

One sheet belongs to one original lesson. Its group, branch, tenant, creator and identity are fixed. One attendance record represents one original student in one lesson, with a composite FK to the same tenant/group/branch enrollment. Unique `(tenant_id, lesson_id, customer_id)` prevents duplicate student events. Student names/contact identities are joined from existing records; no duplicate people, teachers, groups, enrollments or lessons are introduced.

Each record stores an expected/excluded roster flag, one status, optional note (up to 1,000 characters), optional Late minutes (1–1,440), marking Auth user, linked employee when available, marking time, modification user/time and original enrollment reference. Sheets track version, preparation/roster-review time, finalization user/time and correction count/user/time. Audit events retain actor/name, operation, sheet version, reason, record reference and before/after values. Tenant users cannot delete records, reopen finalized sheets or erase audits. Excluded unmarked draft roster rows remain stored and labeled rather than deleted.

## Historical roster rules

The lesson's retained local date in its own timezone must fall within the enrollment's inclusive contractual start/end dates. Pending enrollments with no activation and cancelled enrollments are not expected. First activation honors the stated enrollment start date, including deliberate authorized backdating. Later pause/resume changes apply from their recorded audit instant: a pause today does not erase participation in a past lesson, and resuming later does not invent participation during the pause. Version ordering resolves multiple audit events within one transaction. Withdrawal/completion preserve the prior participation intervals and contractual end date. A pending enrollment withdrawn without activation creates no expected attendance.

Transfer dates retain Step 7's date-level, inclusive source/destination contract; the same transfer date can therefore be eligible in both groups. Each lesson remains a separate event. This increment does not invent a time-of-day transfer cutoff. Pauses cannot be arbitrarily backdated through the existing enrollment UI; a later absence correction changes the attendance mark with an audit reason, not the enrollment audit.

A preview is read-only. An authorized user prepares the attendance roster only after the lesson starts, with every student **Unmarked**. Existing Step 7 expected lists remain retained historical expectations; the reviewed attendance roster is authoritative for attendance. Draft finalization checks the current audited eligibility against that reviewed roster. If it changed, staff must use **Review enrollment roster** explicitly. New students start Unmarked; removed unmarked rows remain as excluded history. If a marked draft row's membership/reference changed, staff must explicitly clear that mark before reviewing; the old mark remains audited. Finalized rosters never change automatically after later enrollment edits, withdrawals, transfers or retroactive registrations.

If an imported/directly inserted enrollment lacks the necessary activation audit, preparation fails with a review requirement rather than guessing eligibility. Normal existing enrollment commands already preserve this audit. Such inconsistent imports need a separately reviewed data repair; no repair, reset or fabricated history is run automatically.

## Attendance workflow

1. Open **Attendance** → Today, Upcoming, Awaiting attendance, Recently completed, or All lessons. Filter actual branch/course/group/teaching employee/dates and sort/page results. Linked teachers see their assigned groups and authorized lessons.
2. Open a lesson's **Attendance sheet**. Review group/course, original/actual teacher, room or online status, timezone/times, lesson notes and expected students. Future lessons are preview-only.
3. Choose **Prepare attendance sheet** after the lesson starts. All students start Unmarked. Save a partially marked draft when needed.
4. Select Present, Absent, Late, Excused or Unmarked. Late minutes are optional. Notes are optional and need no sensitive reason. **Mark page Present** requires an explicit confirmation and affects only the current page; **Clear page to Unmarked** and **Undo page edits** make draft changes reversible before saving/finalization. A visible unsaved-change message and browser-unload warning accompany edited fields.
5. Save each edited page. Draft rows save in bounded batches of up to 200; UI pages contain 20. Stale versions reject rather than overwrite another user. Repeating the exact request returns the same result, while changed request payloads reject. Concurrent prepares create one sheet and concurrent writes yield one version winner.
6. After the scheduled lesson end, review every saved page and finalize. **Every expected student must be marked.** Unmarked finalization is prohibited consistently by the UI and database. An empty expected roster requires a separate explicit confirmation. Unsaved local edits hide finalization controls until saved. Attendance finalization does not complete the lesson, assert delivery, create charges or post payroll.
7. Finalized attendance is read-only for standard teachers. An explicitly authorized user can submit **Save authorized correction**, including a reason of 3–1,000 characters. Prior and corrected values, actor and time remain in the audit; the sheet stays finalized and all expected students remain marked. There is no generic reopen action.

Present means attended; Late means attended late; Absent means expected but not attended; Excused is an explicitly excused non-attendance; Unmarked means no recorded attendance. Sheet counts show saved values, not an attendance-rate report. Future analytics will count Present/Late as attended, Absent/Excused as non-attended, distinguish Excused, show Unmarked separately, and exclude cancelled lessons. No 8D rates/denominators are claimed here.

## Authorization and history

Existing `attendance.view` and `attendance.manage` are reused. New `attendance.finalize` and `attendance.correct` extend the existing role/branch permission system. Owners/Admins and assigned Branch Managers receive branch-appropriate operations; teachers receive view/manage/finalize but no default correction permission. Sales/Cashier/Employee roles gain no attendance-editing permission.

Authorization requires existing lesson access, attendance permission and minimal roster permission (`enrollments.view`) in the actual lesson branch. Branch-wide `groups.view` plus the required attendance grant supports authorized academic staff. Otherwise, an active eligible employee must be the lesson's actual teaching employee to write; the original teacher can read their substituted lesson but cannot mark it while someone else is the substitute. A colleague merely sharing another group/branch receives no attendance access. A specially granted correction permission still respects that lesson scope. HR/branch/role revocation removes future access; Owners retain the historical records even when teachers/groups/courses/rooms become inactive or archived.

Server Actions validate Auth, workspace tenant, current action permission, row IDs, status, note length, version and confirmation fields. Database commands independently authorize and derive student/group/branch identities from the actual lesson and reviewed rows. Tenant-wide academic transaction locks and sheet versions serialize roster preparation, membership review, enrollment changes and finalization. Authenticated clients have read-only RLS grants on sheets/records; raw audit tables remain private, exposed only through checked paginated queries. Financial/tuition/salary data is not returned. Whole Student Profile links remain separately protected by existing all-associated-branches CRM rules.

`/attendance/history` provides basic saved records by date, student/name/identifier, course, group, teaching employee, branch, attendance status and draft/finalized state, with sorting/pagination. It labels cancelled/rescheduled lessons and excluded rows so they cannot be mistaken for regular completed attendance. A lesson's audit view exposes prior corrections. The existing Student Profile provides a link into authorized basic history; full summaries/rates remain explicitly reserved for 8D.

Cancelled/rescheduled lessons retain any existing draft history and reject further ordinary marking/finalization. Missing cancelled lessons create no stored attendance records. A lesson with finalized attendance cannot be cancelled/rescheduled through the old scheduling command; a future controlled administrative scheduling correction belongs to 8B. Marks are never silently copied to a replacement lesson. Existing finance, invoices, allocations, customer credit, guardian identity and salary configuration are untouched.

## Local verification and manual testing

No new dependency, environment variable or credential is required on this configured machine. Start Docker Desktop if stopped, then `npm run db:start`, `npm run db:migrate`, `npm run dev`. Preserve existing data: do not reset. Open <http://127.0.0.1:3000/attendance> after logging in and choosing a business.

1. As Owner, choose a group with an eligible linked employee teacher and an existing active student. Use the existing lesson form to create a past lesson within the group period, with an explicit reason; online/no-room lessons are supported. Lesson completion remains a separate operation.
2. Open the lesson → **Attendance sheet**, confirm the original student/enrollment and click Prepare. Verify all rows start Unmarked, with zero automatic absences. Save a partial draft; then mark/save remaining students across every page.
3. Try Present/Absent/Late/Excused, optional Late minutes and notes. Test the confirmed page-wide Present action, exceptions, Undo and unsaved-change warning. Reload to verify saved records. Attempt finalization while Unmarked students remain; it must be refused.
4. Finalize after the scheduled end and required confirmations. As Teacher, verify ordinary edits and finalized corrections are denied. As Owner/authorized Manager, correct a mark with a reason and inspect the old/new audit values. Confirm the sheet remains finalized.
5. Change relevant enrollment dates while another sheet is still a draft. Review its changed roster explicitly; clear any affected marks first. A student joining later must not appear in earlier lessons; a pause today must not remove previously eligible attendance. Withdrawal/transfer must retain finalized original references.
6. Use a lesson with a substitute: the substitute can mark that lesson, the original teacher can read it, and unrelated colleagues cannot access it. Test a one-branch Manager, Employee, another business and unauthenticated browser; changing IDs must not broaden access. Archive/deactivate a teacher after marking and confirm Owner history remains.
7. Create an empty group lesson: finalization requires explicit empty confirmation and creates no absence. Try future/cancelled lessons and confirm no ordinary attendance can be stored. A retained cancelled draft is visibly distinguished in history. Verify original invoices, debt/credit and guardians remain unchanged after attendance operations.

Automated checks: `npm run check`, `npm run db:test`, `npm run db:lint`; with the app running, `npm run test:integration` and `npm run test:smoke`. Portable tests execute actual migrations in isolated embedded PostgreSQL; native fixtures roll back. Live tests create isolated real local Auth/employee/enrollment/lesson/financial fixtures and submit rendered Next.js forms; those local fixtures remain for inspection. Remaining manual QA: desktop/mobile layout, keyboard/focus and screen readers, browser-native bulk/finalization/correction confirmations, unsaved-change/unload behavior and page-navigation discipline. Rendered-form tests verify server submissions and HTML but do not simulate those browser interactions. Production-size load, earlier password-recovery redemption, sales dragging and printed finance/report layout remain unverified. No 8B–8D functionality, external messaging, automatic billing, payroll, hosted connection, deployment or remote push is claimed.
