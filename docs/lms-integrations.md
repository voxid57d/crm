# Step 7D — Student Profile, academic reporting and invoice integration

The existing Student Profile remains the only education identity: `student_profiles(tenant_id, customer_id)` links to the original shared `customers` record. Groups, enrollments, expected rosters, lead conversions, guardians and financial documents keep their existing IDs. Teachers remain linked employee records. Inspection started from clean commit `ebdca8f`; all 211 baseline portable tests passed. Local Supabase was healthy; the stopped Next.js development server was started on port 3000. Installed Next.js Server Actions and data-security guides were read before code changes.

## Pages and student workflow

- `/academics`: operational dashboard and paginated group capacity/enrollment report. Filters: branch, course, teacher, inclusive date range and capacity. Current selected branch is the initial default; explicitly choosing **All authorized branches** removes that preference without broadening database access.
- `/students/[customer]`: existing contact/education/guardian/CRM activity and separately protected Finance remain. Courses/groups now show current teacher names and group status, with enrollment status filtering and retained previous enrollments. Academic summary distinguishes active courses/groups from all retained enrollments. Student lessons have date/status filters and pagination; linked enrollment charges and minimal academic activity have independent pagination. Attendance is an explicitly reserved Step 8 integration point.
- `/students/[customer]/timetable`: daily, weekly and monthly calendar using the original Student Profile, business timezone and actual generated/manual lesson records. Previous/next/today navigation and lesson status filters work. Calendar pages contain up to 200 events; further pages preserve the student URL and filters.
- `/enrollments/[enrollment]`: linked financial invoices and **Create draft invoice** when authorized. `/enrollments/[enrollment]/invoice` requires review of the original student/debtor, branch, agreed unit price, existing invoices, charge description and dates, plus an explicit confirmation.
- `/finance/invoices/[id]`: retained academic source link when the viewer also has access to its enrollment. Standard draft review/edit, issue/discard and later corrections remain in Finance.

The contact-compatible profile also uses these integrations when a Student Profile is present. No second student directory, Add Student form or competing identity was created. Whole-profile access retains the existing all-associated-branches CRM rule; seeing a minimal group roster does not authorize a whole profile.

## Additive database changes

`20261026000100_enrollment_invoice_links.sql` adds the RLS-protected `enrollment_invoice_links` table and three checked financial integration commands/queries. Composite foreign keys bind an invoice and enrollment to the same tenant, original contact and branch. An invoice has one enrollment source; an enrollment may have several deliberately created invoices. Links are immutable, cannot be deleted by tenant users and survive enrollment withdrawal, transfer and invoice lifecycle changes. Consequently a linked draft cannot be reassigned to another debtor or branch, even through the original finance RPC; the transaction rolls back. Content edits for the same debtor/branch remain supported. Source links do not claim that every invoice line is an unmodified enrollment agreement.

`20261026000200_student_academic_views.sql` adds checked student enrollment/history, summary and lesson read APIs plus a private membership helper. No academic record or financial source is rewritten. Student lesson membership requires a visible enrollment whose dates cover the retained local lesson date, with active/completed/withdrawn status, or an already captured expected-roster reference. Pending/paused/cancelled enrollments do not generate uncaptured expected membership. Frozen rosters retain original enrollment/customer references after withdrawal; they do not assert attendance. Scheduling events are included only for the student's associated, authorized lessons; raw before/after snapshots, private reasons, notes and tuition are omitted. Enrollment events are similarly reduced to operation/time/group/record links.

`20261026000300_academic_dashboard.sql` adds authorized report/options queries. It creates no reporting cache or financial balance table. Every aggregate and page uses checked group/enrollment/lesson/classroom scope; filter UUIDs only narrow those scopes. Public/anonymous execute grants are revoked, and tenant users have no direct insert/update/delete grants on source links. Raw existing academic and finance tables retain their original protections. Migrations are applied with `npm run db:migrate`; never reset the database to install them.

## Permissions

No competing permission engine or new role is introduced. Owners/Admins retain business scope; Managers stay within assigned branches. Teachers report only on their assigned groups and permitted lessons (including a one-off substitution for lesson counts); Employees receive no automatic academic access.

Student summary/timetable APIs require authorized whole-contact `customers.view`, the original Student Profile, and per-record enrollment/lesson authorization. Academic pricing remains independently protected by `enrollments.view_pricing`. Student activity does not return private academic snapshots just because the viewer can open the contact.

Creating an enrollment draft requires visible enrollment and agreement pricing, invoice view/create in the actual enrollment branch, and existing whole-contact access. The existing finance service additionally checks the active contact, branch and contact-branch association. Teacher defaults grant none of this financial access. Linked invoice reads require both enrollment and existing invoice authorization; a financial-only viewer receives no academic source metadata. Inaccessible invoice counts and amounts are not returned through academic APIs or RLS.

The server action re-authenticates and checks current workspace/record scope; the database independently repeats authorization. The client supplies an enrollment reference and reviewed dates/description, never authoritative tenant membership, price, branch or debtor. The database derives those from the locked enrollment. Academic request receipts serialize writes by tenant, bind actor/payload and protect retries; the existing invoice service supplies the financial audit receipt. Concurrent identical submissions return one draft. Changed payloads, stale agreement versions and revoked privileges are rejected.

## Financial boundaries

Draft creation calls the existing `save_invoice_draft` service, rather than writing a parallel invoice or ledger. It creates one line at quantity `1` and the exact agreed tuition string (including values beyond JavaScript's safe integer range). Monthly/per-lesson prices are explicitly one agreed unit: staff must describe the billed period or lesson. There is no inferred billing cycle, recurring billing, auto-issue, collection, allocation or payroll. Separate deliberately submitted requests may create additional invoices; staff must review the displayed existing invoice history to avoid billing a period twice. Zero-price drafts remain governed by existing finance rules; issued totals must be positive.

Catalog changes never rewrite agreed enrollment terms or linked drafts. Draft edits use normal Finance behavior and cannot silently change original student/branch. Only the existing explicit issue command creates a receivable; draft creation changes the document list but leaves outstanding debt, payments, allocations and available credit untouched. Enrollment status/transfer and report reads never move or rewrite invoices, payment sources or ledger entries.

**Student** means education recipient. A **guardian** remains a separate related contact. The **invoice debtor** in this bounded workflow is the existing student's shared contact. A **payer** is whoever provides the money and is not assumed to be the student or guardian. Current payment records have notes/reference fields but no normalized separate payer identity; descriptive notes do not establish a debtor or payer relationship. Normalized guardian-as-debtor or third-party debtor/payment relationships are not implemented; the form explains this limitation instead of silently billing a guardian or creating another student. A future finance increment can add explicit debtor relationships without replacing identities or rewriting posted history.

## Dashboard definitions and limits

The date range is inclusive and bounded to 366 dates. Groups and active enrollments must have effective dates overlapping the range; status is the current status, rather than reconstruction of historical state. Unique active students count distinct original customer/Profile references, while active enrollments count rows. A student in three groups contributes one unique student and three enrollments. Active offered courses count distinct active catalog entries delivered through matching planned/active/paused groups; unused catalog entries remain in Courses.

Teacher counts use current, eligible group assignments. A teacher filter selects current group assignments for group/enrollment metrics and the effective actual teacher, including substitutes, for lesson metrics. Today uses the business timezone; lesson totals use concrete records in the selected range; upcoming means a scheduled lesson after now; completed counts retained completed records. Ungenerated weekly reservations are not fabricated events. Cancelled/rescheduled records remain available in student and main timetable filters.

Reserved seats include pending, active and paused enrollments. Near capacity means at least `ceil(capacity × 0.8)` and below full; at capacity is at least capacity. Only open groups (planned/active/paused) count in those cards. The capacity selector narrows the group report; metric cards retain the branch/course/teacher/date scope. Seat/enrollment data require enrollment access. Other inaccessible data are excluded from aggregates.

Active classrooms are configured active physical rooms in active authorized branches, **not time-slot availability**. Course/teacher filters limit that count to branches of matching groups. Report pages and student lists contain 20 rows; student calendars contain 200. Sorting is deterministic (report by name/ID, lessons by start/ID, history by time/ID, invoices by creation/ID). Student lesson lists allow 366 dates; calendar requests allow at most 42 dates. This is operational reporting, not an attendance, statutory, or historical-state analytics warehouse.

## Testing locally

No new dependencies, environment variables or credentials are required on the configured machine. Start Docker Desktop, then `npm run db:start`, `npm run db:migrate`, `npm run dev` if services are stopped. Open <http://127.0.0.1:3000>. Preserve local data; do not reset.

1. As Owner, open **Academic overview**. Compare all branches with one branch, course, teacher and date filters. Enroll the same existing student in two groups: unique students must remain one while active enrollments become two. Try near/full capacity filters and page through the group report.
2. Open that original Student Profile. Confirm guardian/contact information, existing invoice/payment/debt/credit records and original URL remain. Check current groups, previous enrollments, teacher names, group status, enrollment status filters and academic event links.
3. Create/generate lessons using the existing group workflow, including a completed past lesson and a cancelled future lesson. On the Student Profile, filter dates/status and open **Student timetable**. Try day/week/month and previous/next/today. Other students' groups must not appear. After withdrawal, a captured completed lesson remains; future lessons outside enrollment dates disappear.
4. Open an enrollment → **Create draft invoice**. Review the displayed agreed price and existing charges. Enter a period/lesson description and dates; confirm the debtor. Save and verify a real Finance draft, original contact/branch and source link. Return to the enrollment and Student Profile to see it. Debt/credit must remain unchanged until an authorized explicit issue/payment action.
5. Review/edit the draft through Finance; the source student/branch cannot change. Issue only if you intend to create a real local receivable. Existing invoices are never transferred by student/group transfers. Guardian billing is intentionally unavailable in this workflow.
6. Use separate browser profiles for Teacher, branch-limited Manager, Employee and a different business. Teacher reports must remain assigned-only and contain no tuition/invoice data. Teachers/Employees cannot create drafts by visiting the URL or submitting action/API requests. Manager filters and edited IDs cannot expose another branch or a shared whole profile beyond existing access. An unauthenticated visitor is redirected to Login.

Run `npm run check`, `npm run db:test`, `npm run db:lint`; with the app running, `npm run test:integration` and `npm run test:smoke`. Portable tests execute real migration SQL in isolated embedded PostgreSQL. Native tests roll back fixtures. Integration tests use real isolated local accounts/records and rendered Next.js form submissions; records are retained for inspection. See [verification](verification.md) for final actual results.

Visual/mobile/keyboard/focus and native browser confirmations remain manual QA, along with earlier recovery-link redemption, sales drag interaction and print layouts. Production-scale load remains unverified. There is no attendance marking, homework, gradebook, student/parent portal, payroll, automatic billing, hosted connection, push or deployment in this increment. Steps 7A–7D complete the core LMS; Step 8 needs its own authorized scope.
