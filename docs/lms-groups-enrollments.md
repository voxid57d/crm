# Step 7B: groups, teachers and enrollments

## Inspection and design

The clean baseline is commit `ea2af6e` (7A). Strict TypeScript and all 178 portable tests pass before changes. Existing local Docker/Supabase data is retained; the running Next.js server on port 3000 is reused. Installed Next.js security and Server Actions guides were read. No dependency, hosted connection, database reset or separate student/teacher identity is needed.

Reuse `courses`, branch `classrooms`, `student_profiles(tenant_id, customer_id)`, shared `customers`, `employee_branches`, linked employee Auth accounts and the existing permission engine. Groups belong to a fixed branch/course. Student enrollments reference the composite Student Profile key, not a new person. Teacher assignments reference employees; eligible teachers need active employment, a linked active account, the group branch in employment assignments and explicit teaching permission in that branch. This keeps teaching eligibility independent of job-title text. Assignment history survives HR/role changes; those changes revoke teacher access immediately.

Only 7B is authorized. Weekly schedules, lessons, substitute assignments, calendars/conflict checks, full profile timetable/invoice integration and academic dashboard remain 7C/7D. Online groups may have no classroom. Group/course enrollment counts will come from actual records. No automatic billing or salary calculation is added.

Groups have planned/active/paused/completed/cancelled/archived lifecycle, optional default classroom and bounded capacity. Pending/active/paused enrollments reserve seats; paused students retain seats. A partial unique constraint prevents duplicate open enrollment in one group. Capacity-changing, enrollment and transfer commands are serialized per tenant and transactional. Versions reject stale edits; private request receipts make retries safe. Terminal enrollment agreements retain their own exact price/model/currency; course edits do not alter them.

Transfers require authorization in both actual groups and access to the original shared student. They close the source enrollment and create a linked destination enrollment atomically; old agreements, identities, branches and financial references remain. Adding a missing destination student branch is an explicit option requiring existing CRM update permission in every old branch plus the new one. Old student branch links are never silently removed. A failed transfer changes neither enrollment nor branch associations. Group completion/cancellation requires open enrollments to be closed first; no implicit bulk status or financial change occurs.

Teachers receive assigned-group reads and minimal academic rosters only, with no salary, debts, payments or agreed tuition through academic APIs. General group view grants remain branch-scoped; mutation checks use actual records. Enrollment pricing has a separate permission. Raw NUMERIC fields and command/audit receipts have no client read grants. Historical events are immutable and only authorized administrators can read change snapshots. Roster/profile links continue using the canonical `/students/[customer]` identity and existing CRM checks.

Implementation plan: additive schema/permissions/integrity; transactional group/teacher/enrollment/transfer commands; authorized paged query DTOs; reusable forms and protected routes; existing student creation return link and Student Profile enrollment list; portable/native/live tests including simultaneous last-seat enrollment and rollback of failed transfers; full regressions/build/types/docs. No destructive data operation is part of this increment.

## Implemented schema and APIs

Five additive migrations (`20261025000400`–`20261025000800`) are applied locally. They add schema/roles, commands, query DTOs, the date/filter contract and an authorization recheck. No existing identity or financial source table is replaced. Date conversion is STABLE because PostgreSQL text-to-date conversion depends on DateStyle; inputs still require an ISO date.

| Table                       | Contract                                                                                                                                                    |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `study_groups`              | Fixed tenant/branch/course, optional same-branch classroom, names/code, start/end, capacity, lifecycle and optimistic version                               |
| `group_teacher_assignments` | Existing employee, group and branch, primary/additional flag, assignment/end actor and timestamps; ended records retained                                   |
| `student_enrollments`       | Composite existing Student Profile FK, fixed group/branch/customer, enrollment/effective dates, status, exact agreement, notes, transfer source and version |
| `lms_commands`              | Private actor-bound request/payload/result receipt, unique within a tenant                                                                                  |
| `lms_events`                | Immutable group/enrollment before/after snapshots, operation, actor, reason and time                                                                        |

All five tables have RLS. Only authorized group and teacher-assignment metadata has direct client SELECT grants. Enrollment reads use checked DTO APIs; raw NUMERIC tuition, command payloads and event tables have no client grants. No client directly inserts, updates or deletes these records. Tenant-composite foreign keys prevent cross-business and cross-branch references. Group codes are unique within their branch when supplied. Teacher assignments allow at most one current primary and one current assignment per employee/group. Closed assignments cannot be rewritten or deleted.

Mutation APIs: `save_study_group`, `change_group_status`, `set_group_teachers`, `create_student_enrollment`, `update_student_enrollment`, `transfer_student_enrollment`. Read APIs: `lms_options`, `group_directory`, `study_group_details`, `enrollment_directory`, `student_enrollment_details`, `group_student_choices`, `group_teacher_choices`, `group_teacher_filters`, `lms_history`, `course_group_summary`. The existing `private.has_permission` remains the authority. Private helpers are not Data API entry points.

Commands lock the tenant before resources, matching existing CRM/catalog lock order. Short mutations are serialized within a business, while unrelated tenants remain independent. The receipt and audit events commit with the change. Matching exact requests replay their original ID only after renewed authorization; mismatched actor/payload fails. Integer versions reject competing edits/transfers. A partial unique index prevents concurrent duplicate reserved enrollments, and a deferred database capacity constraint independently rejects overbooking, including privileged direct inserts. Capacity decreases cannot displace reserved students. Classroom capacity cannot be reduced below current planned/active/paused group limits.

Directory, roster, selection and history queries use batches of 20 with exact authorized totals. Group filters include branch/course/assigned teacher/status, literal name/code search and sorting. Enrollment filters include group/student/branch/status, literal name/identifier/group search and sorting. Teacher filters reveal only teachers attached to visible groups. Search selectors retain already-assigned teachers while paging eligible additions. The course page shows actual group and enrollment counts **within the viewer's group scope**, not fabricated tenant totals. A student enrolled in multiple groups contributes multiple enrollment records; group details separately label unique active students.

## Lifecycle and agreement rules

Group transitions: planned → active/cancelled; active → paused/completed/cancelled; paused → active/completed/cancelled; completed/cancelled → archived. Group completion, cancellation and archive require every pending/active/paused enrollment to be closed first. Group pauses do not silently change individual enrollment statuses. Terminal group configuration and assignment history cannot be edited. Branch/course identity stays fixed; correct an unused mistaken delivery by cancelling it and creating the right group.

Enrollment transitions: pending → active/cancelled/withdrawn; active → paused/completed/withdrawn; paused → active/completed/withdrawn. Pending/active/paused reserve one seat each regardless of dates; pauses retain their seats until an explicit terminal action. Terminal records release their seat immediately and cannot be edited. A student may re-enroll later through a new retained record. Counts are based on explicit current statuses; calendar-effective occupancy is not implemented in 7B.

Agreements accept nonnegative decimal strings including free `0.00`, up to 16 whole digits and two fractional digits, and reject JSON numeric money/excess precision. Currency is UZS. Price/model/currency are fixed at creation and retained through status changes; each transfer has an explicitly reviewed destination agreement. A course price change cannot retroactively change an enrollment. Academic administration notes are hidden from ordinary roster readers and must not contain salaries/debts or unrelated confidential finance data.

Group dates must be ordered and retain all recorded enrollment periods. Enrollment dates cannot be future enrollment-record dates; effective starts may be future planning dates within the group period. Existing non-pending effective starts cannot change. Completion/withdrawal requires a nonfuture end on/after the effective start; cancelling a future pending enrollment can leave its end unset. Activating/resuming an enrollment requires an active group/branch and nonarchived student. Archived courses reject new groups/enrollments but preserve existing agreements and status history. Inactive classrooms remain historical references; new enrollments/group activation require usable authorized resources. Online groups use a null classroom.

Transfers are immediate, cannot target the same group and require an open source, a date within its original period no later than today, an authorized planned/active target with space and a compatible destination status. Future pending students can be cancelled/re-enrolled; future-dated transfers are deferred. The transfer date becomes the source end and destination start; the new record's enrollment date is business-local today. The original source becomes withdrawn and the new record points back to it. Neither source nor destination financial references are created, moved or rewritten. A full/unauthorized/invalid destination rolls back the entire operation, including source status/history and any explicitly requested student branch addition.

## Permissions

Owner/Admin receive the new group/enrollment grants within their business. Branch Managers receive them within assigned branches. Default Employees gain none. Custom role permissions can be configured through the existing role page.

Teachers receive `groups.view_assigned`, `groups.teach` and `enrollments.view` in assigned branches. They additionally need a current employee assignment to the particular group. They receive no general `groups.view` grant, so a branch assignment alone does not expose every group in that branch. Linked employment status, membership, branch permissions and teaching eligibility are rechecked at read time. Removing employment/branch/role eligibility revokes access immediately while preserving assignment history.

`groups.view` grants ordinary authorized branch group visibility; `groups.create/update/archive/assign_teachers` authorize separate operations. `enrollments.view/create/update/transfer/withdraw` remain independent. Tuition read/agreement creation additionally requires `enrollments.view_pricing`; transfers require pricing access to the source and destination and create/transfer/withdraw access in the actual scopes. Group mutations cannot be authorized by an ID or cookie alone.

Teacher roster DTOs contain academic name/identifier, group, dates and status. They omit agreed tuition and private notes/history, phone/guardian/contact details, salaries, debts, invoices and payments. Canonical Student Profile links are shown only if existing CRM rules allow that whole shared contact. Academic permission never grants broader CRM or financial access. A shared student may appear in a permitted minimal roster while their full CRM profile remains restricted by the existing all-branches rule. No second Student directory/profile or Teacher identity was created.

## Manual testing

The configured environment needs no new package, credential or variable. Open <http://127.0.0.1:3000>, log in, and select your business. To restart later: start Docker Desktop, `npm run db:start`, `npm run db:migrate`, `npm run dev`. Never reset the database to apply migrations.

1. Create an active course and optional physical room using 7A. Open **Groups → Add group**, choose the branch, course, dates and capacity (try 2), and optionally the room. Online groups can leave the room empty. Save, edit the name/code and inspect group history.
2. Create employee teachers with branch assignments through **Employees**. As Owner, invite their confirmed local accounts with the Teacher role and accept each invitation using the matching account. Open a group → **Assign teachers**; select primary/additional teachers and exactly one selected primary. Multi-branch teachers need employment and account authorization in each relevant branch.
3. Open **Enroll student**. Search existing students or choose **Add Student using the existing form**. Saving returns to this group's enrollment form, and reusing a duplicate match retains the original ID. Review the price/model/status and save the agreement separately. Creating a student alone does not auto-enroll or bill them.
4. Enroll two students in the capacity-2 group. A third must fail. Try shrinking capacity below reserved seats. Activate the group, activate an enrollment, pause and resume it; a paused enrollment keeps its seat. Withdraw/complete using today's valid end date, or cancel a pending enrollment, to release a seat.
5. Change the course template price and verify the old agreement is unchanged. Open the original Student Profile to see real group/enrollment history alongside existing guardians and authorized finance information. No invoice/payment should appear merely because of enrollment.
6. Create another group (optionally at another authorized branch). On an enrollment, choose **Transfer to another group**, search/select the destination, review its agreement, supply today's transfer date and a reason, and explicitly approve a missing branch addition if authorized. Verify source withdrawal, destination link and original Student Profile ID. A full destination must reject the transfer without changing the source or its branches.
7. Close reserved enrollments before completing/cancelling a group, then archive it. View historical enrollments and teacher changes; records remain. Search/filter/sort directories and follow pagination.
8. Use separate browser profiles for Owner, assigned Teacher, branch-limited Manager and another business. Teacher sees assigned groups only, minimal rosters and restricted agreement details; Manager cannot manage other branches; another business cannot retrieve the records by changing URLs or RPC IDs. Archive a linked employee and confirm access is revoked immediately.

Automated commands: `npm run check`, `npm run db:test`, `npm run db:lint`; with the server running, `npm run test:integration` and `npm run test:smoke`. Native fixtures roll back. Live fixtures are isolated real local accounts/business records retained for inspection. See [verification](verification.md) for final counts/results.

Remaining manual QA: responsive visual layout, keyboard/focus, confirmation-dialog interaction and production-size load. Existing recovery-link redemption, sales dragging and print/PDF layout retain their earlier manual limits. This increment has no schedules, lesson generation, timetable, attendance, payroll or invoice generation. Guardian/debtor/payer identity distinctions and existing finance services remain unchanged.
